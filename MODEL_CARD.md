## Intended use

**Primary use.** Rank cash-on-delivery orders by return-to-origin risk so a *bounded,
reversible, defensive* action can be selected: approve, step up verification, offer
part-payment, offer conversion to prepaid, hold for review, or escalate to a human. The
model is decision **support** — every action it triggers is drawn from a closed set, cites
a policy clause, is written to an append-only audit log, and can be overridden by a human
reviewer.

**Intended users.** Risk-operations analysts at a merchant or payment aggregator, working
a review queue.

**Out of scope — do not use this model for:**

- credit, lending, insurance or employment decisions;
- permanent account bans, blocklisting, or any irreversible penalty;
- anything offensive: evading detection, generating fraud, or probing another system's
  controls. The project is defense-only by construction;
- deployment on real order flow **without** retraining and recalibrating on that flow —
  see *Limitations*;
- inferring anything about an individual beyond a single order's return risk.

---

## The model

- **Algorithm.** LightGBM gradient-boosted trees (binary objective), early-stopped on
  validation PR-AUC, wrapped in an isotonic calibrator fitted on the validation split.
- **Why calibrated.** Every downstream rupee decision is a threshold on a probability. An
  uncalibrated score makes the cost arithmetic meaningless, so calibration is a
  correctness requirement here, not a refinement.
- **Why no resampling.** The positive rate is ~17% — moderate imbalance, not the sub-1%
  extreme. SMOTE or class weights would distort the predicted probabilities the cost model
  depends on. We train on the natural distribution and get the honest operating point from
  cost-based thresholding instead.
- **22 features**, all observable at checkout: order attributes (value, category, distance,
  hour), address quality, buyer tenure, payment mode, pincode serviceability, plus
  target-encoded pincode/buyer history, velocity counts, and shared-device graph counts.
  `GET /model_meta` returns the exact manifest for the served artifact.
- **Companion, not a feature:** an IsolationForest anomaly score runs alongside as an
  unsupervised trip-wire for cold-start and zero-day patterns. It can escalate an order the
  supervised model considers safe; it never overrides a rule.

## Training data

**Synthetic, and disclosed as such everywhere it appears.** No clean public dataset of
Indian COD/RTO orders exists. Orders are drawn from an explicit causal model of the
published RTO drivers (payment mode, address completeness, pincode risk, buyer reliability,
distance, category, order value, first-time-buyer status, device-sharing fraud rings), with
per-payment-method intercepts calibrated so the marginal rates land in realistic bands
(~27% COD, ~4% prepaid). Generator: `src/data/generate_synthetic_cod.py`, seed 42.

The *true* latent drivers — a pincode's underlying risk, a buyer's reliability, ring
membership — are written to a **separate** file and never enter the feature matrix. The
model must estimate them from observable history, exactly as it would in production.

- 20,000 orders · chronological split 14,000 / 3,000 / 3,000 (train / val / test).
- The test split keeps its **natural** RTO rate and is never resampled.
- **No PII and no protected attributes.** No name, phone, email, or address text reaches the
  model; city tier, category and order value are commercial variables. Address *quality* is
  a completeness score, not the address.

## Evaluation

Full results, with bootstrap confidence intervals, in
**[docs/evaluation.md](docs/evaluation.md)**. The methodology commitments:

1. **Split by time, never at random.** Train precedes validation precedes test.
2. **Out-of-fold by construction.** History features use only orders that occurred earlier;
   a row's own label can never enter its own feature. Guarded by tests.
3. **Outcome-availability lag.** Label-derived history is held back **7 days** — an order
   placed today cannot know whether yesterday's order was returned. The predictive cost of
   this correction is measured and published.
4. **The operating threshold is fitted on validation and frozen** before the test split is
   scored. The test-optimal *oracle* threshold is also reported, purely to quantify the
   optimism we declined.
5. **PR-AUC against prevalence, plus a rupee cost curve** — never accuracy, which at a 17%
   base rate rewards a model that catches nothing.
6. **Baseline ablation.** The model is compared against an expert scorecard and a logistic
   regression on identical terms, with paired bootstrap intervals on the gap. Where the
   interval spans zero, we say so.
7. **Failure-mode matrix.** False-positive burden is broken out by payment mode, city tier,
   category, order value, buyer tenure and address quality.

## Ethical considerations and risks

**A false positive lands on a real person.** The dominant risk is a genuine customer being
frictioned. Three design choices follow from that:

- **Dynamic friction, never a block.** The worst routine outcome is being asked to confirm
  an address or being offered a prepaid link — one step to clear yourself.
- **The threshold is chosen on cost, not on a leaderboard.** A blunt "block all COD" policy
  is measurably *more* expensive than approving everything, because the friction it inflicts
  on good customers outweighs the fraud it stops. That result is the argument.
- **The disparity is published.** §6 of the evaluation names the groups that absorb the most
  friction — tier-3 cities, first-time buyers, higher-value orders. This is an operational
  harm audit, not a legal fairness audit: no protected attribute is used, and the variables
  involved are commercial. It is monitored rather than explained away.

**Explanations.** Reason codes are grounded: SHAP attributions and retrieved policy clauses
are computed first, and the language model may only narrate those facts. It cannot change a
score, invent a factor, or select an action outside the closed set.

**Automation risk.** No decision is final. Every decision and every human override is
written to an append-only SQLite log with database triggers blocking `UPDATE` and `DELETE`.

---

## Limitations

- **The world is synthetic.** The metrics are real and measured on held-out data, but the
  data-generating process is ours. On real order flow the model must be retrained and
  recalibrated before any rupee claim is repeated.
- **The cost model is assumed.** `c_FP` and `c_FN` are stated, not audited. Every rupee
  conclusion moves with them; the dashboard slider exists so a reviewer can substitute
  their own.
- **The action efficacies are assumed.** How much of a return a step-up actually prevents is
  unmeasurable without a counterfactual experiment. The band cut-points depend on it, so the
  assumption is swept rather than asserted.
- **LightGBM is not shown to beat logistic regression** on this dataset — the paired
  interval spans zero. It is retained for its handling of categorical/interaction structure
  and for per-order SHAP attributions, not on a claim of superior accuracy.
- **Recall is modest by design.** At the frozen threshold the model catches roughly a third
  of returns. It is a ranker that routes attention, not an oracle that stops fraud.
- **No drift monitoring.** A production deployment would need population-stability
  monitoring and periodic recalibration; neither is built here.

## Reproducing every number

```bash
python -m src.data.generate_synthetic_cod --n 20000 --seed 42
python -m src.model.train           # trains, calibrates, freezes thresholds on val
python -m src.model.full_report     # regenerates docs/evaluation.md + figures + JSON
pytest -q                           # the leakage and economics guards
```

Deterministic throughout: fixed seeds in the generator, the model, and the bootstrap.
